# 直接基礎・支点・全体の設定と、読込・保存の性質

## 直接基礎の支点と別枠の照査データ（2026-10-17、旧版 5.1 の橋脚の NDU を見本 PDF と NDT で照合して観測）

- 座標：NDU の座標原点は任意の節点（観測したモデルでは節点5）、y は下向きだった。原点や符号の違いを形状不一致とみなさない。`-2.980232E-07` のような値は NDT の表示精度では 0.000 で、ゼロへ修正しない。
- 長さ 0.010 m の非線形要素（他は剛域）があっても、全長に 0.010 m を足さない。
- 直接基礎のモデルは `SuppotNum=3`、`SuppotRow=2`、`FootRow=1` だった。並進ばね2行と直接基礎回転ばね1行を合わせた3支点データで、NDT にも3行がある。杭周面支持専用の `SuppotNum=SuppotRow` という部分仕様を直接基礎へ流用しない（正しい数え方は下の「杭基礎の NDU」の `SuppotNum` の項）。
- 解析用の `FootInfo<n>` は節点、B、L、kv（kN/m³）、Df（m）、φ（度）、KR2 などを持ち、第10フィールドが平均有効単位重量 γ2（kN/m³）。見本の表示値（例：Df=3.8）は丸めで、入力（3.78）を丸めた表示値へ変更しない。
- `CHOKU_KISO<n>` は別枠の照査用データ（継続行がある）。解析用 `FootInfo` と同一の入力だと決めつけない。見本に入力表がなく、意味・同値性の全確認はできていない。解析入力が一致しても基礎照査設定全体の再現を保証しない。
- `ChokuKisoNum`・`CHOKU_KISO<n>`・`CHOKU_KISO_Link<n>=1,<節点>`（照査位置）があると、解析後に JRSNAP の基礎照査機能（`S_SubstCheck.exe`）が `<DB1名>_Output_Chokukiso.csv` などを書け、Aggre-SE の直接基礎の照査はその値を使う。`ChokuKisoNum=0` だと Aggre-SE は DB1 から求める（スキル `structural-jrsnap-input` の engine.md、スキル `structural-aggrese`）。
- `SoilRenkeiFile<n>`（SOIL-JR 連携の旧絶対パス）、`NDTPath`（旧出力先）、`Tisou`（地層）に古いデータが残っていることがある。根拠がなければ保持し、再連携・再出力を行わず未確認として報告する。

## 旧版のファイルを 5.2・5.3 で保存したときに足される項目（2026-10-17、`Virsion=5.1.10.S.4` の1件で実測）

スキル `structural-jrsnap-input` の save-ndu.ps1 の検査モードで、インストール済み V52/V53 の読込・保存処理を一時コピーに実行した。両版とも再保存がバイト一致し、保存された本文は同一で、ヘッダーはそれぞれ `5.2.3.S.4` / `5.3.1.S.6`。原本との差は、ヘッダー以外では次の7項目だった。

1. `DataInfo` 末尾に `,0,0,0`。
2. `SectInfo<n>` 末尾に `,0,0`。
3. `TanbuShiji<n>=0,0` 行追加。
4. `SectSafe<n>` 末尾に `,1.3`。
5. `FootInfo<n>` 末尾に `,20,-3.402823E+38`。
6. `CHOKU_KISO<n>` の先頭行末尾に `,20`。

これは1つのモデルに対する保存処理の実測で、マニュアルの新版既定値を旧モデルに一律適用しない。行追加による位置ずれを含む `BodyChangedLines=137` は、137個の入力値が変わったという意味ではない。原本へ新版保存を反映する場合は実際のキー単位の差分を確認する。

## 両端固定 M-θ 部材の Vmu・Vud のチェック（2026-10-22、JRSNAP 5.2-L03）

基本条件の画面の「破壊形態の判定において、両端固定支持された M-θ 部材の Vmu と Vud の値を計算して照査する」（操作説明書 2-51 ⑫）。

- **`DataInfo` の最後の欄**（0＝なし、1＝あり）。コードで確認（`JRSNAP_Input.exe` 5.2.3.1 を逆コンパイル）：画面は `frmEditKihonJyoken.chkVasud`（`G_intSNAP_FLG == 1` のときだけ表示）、値は `mdlGlobal.G_intChkVasud`。`mdlDataFile.cs` は `DataInfo` の整数16欄・実数4欄のあとに `KISOFLG, KISO_SHUBETU, NiniZahyoFlg, SendanSpan, [GanmaC], ChkVasud` を書く（`GanmaC` は `G_intViewFlg[22] == 1` のときだけ書く。読込みは `GanmaC`・`ChkVasud` の順に読む）。
- Batch の見本「T形両端固定」（26欄）では第26欄。0→1 にしただけの NDU を runner の `--analyze false` で書き出すと、NDT の差は DA ブロック1行目の1文字（`GanmaC` の次。1 なら `1`、0 なら空白）だけだった。
- 解析すると、両端固定（`TanbuShiji<n>=2,<部材長 mm>`）の断面の両端の M-θ 部材で、総括表の Vmu が `|Mm1 − Mm2| / L` になる（実アプリで確認。DB1 の値はスキル `structural-aggrese` の outputs.md）。見本（開発機のみ。structural-mcp の repo のルートから）：`Batch/tests/JRSNAP_Ver5.2-L03/08_両端固定のVmu・Vud(V52-L03)/`。
- **`SendanSpan`（`DataInfo` の実数4欄のあとの4番目、全体の第24欄）は「場所打ち杭の杭頭部への等価せん断スパン法の適用」**（操作説明書 表2-19）：0＝適用しない、1＝適用する（Vdd に側方鉄筋を考慮しない）、2＝適用する（Vdd に側方鉄筋を考慮する）。解析で確かめた（JRSNAP 5.2-L03、WebRamen R6d、2026-10-26）：1・2 にすると杭頭の要素の `VddVasud` が入り、Vud は Vyd と Vdd の大きいほうになる（RC 円形の杭、圧縮側で 1166.5 → 1 で 1501.7、2 で 1640.3）。**`KGInfo<n>` の第4欄に 1/β（m）が要る**（0 のままだと LOG にエラー 1311「杭基礎設定用データ：等価せん断スパン法の適用時は1/βの入力が必要です」で解析が止まり、runner は `ANALYSIS_FAILED`）。適用すると解析は各 Case の DB1 の横に `<DB1名>.CSV`（等価せん断スパン法の帳票。Shift-JIS）を書く。`.ATR` に「W:場所打ち杭の杭頭部に等価せん断スパン法を適用しています.」。
- 旧版を保存したときに `DataInfo` 末尾に足される `,0,0,0`（上の節）は、`SendanSpan`・`GanmaC`・`ChkVasud` と推定（未確認）。5.3-L01体験版2 は調べていない。

## 5.2-L03 の読込の制約（2026-10-17、インストール済み 5.2-L03 の読込・保存処理で一時モデルを確認）

- reader は行の位置と順番に依存する。キーが同じでも `Member_BunpuBane` や `ShabuzaiMeInfo` を別ブロックへ移すと読込に失敗する。名前を辞書へ読み込めただけでは実アプリ互換を保証できない。
- `TishouNum=0` にしても `Tisou=` の空行は必要だった。行ごと削除すると後続読込で空文字から Byte への変換に失敗した。不要な旧地層の値を除くことと、構文上必要な空レコードを除くことを区別する。
- 1要素1部材の構成、`ChokuKisoNum=0`、照査リンク無効、`SRenkeiNum=0`、`TishouNum=0` のモデルでも、解析用 `FootInfo` を保持して読込・保存できた。旧照査・連携データを新規のモデルへ自動コピーする必要はない。
- `DataInfo` 第20フィールドの 0.001 は収束判定値 FTM で、変位増分そのものではない。変位目標値と増分数は別項目。
- `TanbuShiji=0,0` は断面照査側の部材端条件で、骨組の基礎支点条件ではない。
- `SectJikuNum` の上下面引張主筋段数 N は、`SectRein` の**書いた行の順**で先頭 N 行・末尾 N 行を引張鉄筋とする。距離の順に並べ替えない（2026-10-27、5.2-L03 の実機で確認：P7橋脚の線路方向の .ndt で、2行目に 3555（下側の 2段目）を書いて N＝2 にすると、M-θ 自動算定のエコー `%TEMP%\RTRI\RC・PHC_EchoPath_正No1.csv` の `<ArgSteel>` で 100 と 3555 が `Kind=1`（上の引張）、末尾2行が `Kind=2`、ほかが `Kind=3` になり、`Pt`・`[PullOut] Cs2`（段の間隔 3555−100＝3455）もその2行から計算された。DB1 の `StlBar.Item` も書いた順のまま）。だから主鉄筋の段の間に側方鉄筋などの行があるときは、主鉄筋の行を先頭・末尾に寄せて書けば N＝主鉄筋の段数にできる。距離の順に書いた表なら、先頭から最も内側の主鉄筋の段までの行数が N になる（操作説明書 90・530頁、内部の DRTU/DRTL/DRTUV/DRTLV）。
- 引張鉄筋の選び方を確かめるには、荷重〜変位曲線ではなくエコーの `Kind` を見る。P7 の線路方向では、引張鉄筋を 100・345 から 100・3555 に変えても荷重〜変位曲線は 1/1000 程度しか変わらなかった（N は抜出しの段の間隔と Pt などに効くだけ）。エコーは解析のたびに上書きされる。
- 実アプリの保存で数値の字面が正規化されるため、バイト差分に加えて意味と参照の照合が要る。
- NDU の読込・再保存は、画面の確認、NDT 出力、解析実行、耐震安全性の確認を意味しない。

## 節点の番号・破壊形態・節点荷重（2026-10-20、WebPier が書いた P7橋脚の NDU を 5.2-L03 で解析して観測）

- **節点番号は上から、同じ高さでは左から**付ける（操作説明書 2.1.6・図2-9）。要素の i 端は小さい番号（鉛直要素は上、水平要素は左）。この順でない NDU も読込・NDT 出力はエラーなく通るが、桁受けの節点・要素を末尾に足した橋脚で解析が破綻した（降伏震度 0.000〜0.010、1回目の変位増分で「第2トライアル回数制限値到達」）。左上から振り直すと正常に解析した（線路方向 Kheq 0.340、直角方向 0.551）。
- `NonLinInfo<n>` の第4フィールドは**破壊形態**：1＝曲げ、2＝せん断（NDT の AP カードの `S`）。操作説明書（表2-67・注⑧、PDF 142〜143。付表1-5 のエラー 817）は「低せん断スパン比の要素は S、曲げ破壊先行形の要素は 0（または空白）」。**低せん断スパン部材は La/d＜1.25**（利用者 2026-10-28）。付録4 は「③1.25≦La/d＜2.0 の変形性能を見込める低せん断スパン部材」をせん断変形を考慮した部材角の適用範囲に挙げるが、これを「低せん断スパン部材＝1.25≦La/d＜2」と読まない。1.25≦La/d＜2 の部材は曲げ（1、`S` なし）にする（利用者 2026-10-28。WebPier は決定114 で柱をいつも 1 にした）。Batch の見本「T形両端固定」の地中梁（La/d≒1.4）で `NonLinInfo7=1,3,1,2,…`。2 にした柱を 5.2-L03 はエラーなく解析した（`解析実行Err.log` は空）。
- `NonLinInfo<n>` の第6・第7フィールドは M-φ 要素の i 端・j 端の**抜出し量補正係数**（操作説明書 表2-67・注③）：0＝部材接合部からの軸方向鉄筋の抜出しを考慮しない、1＝考慮する（M-θ は入力によらず 1 として計算）。**0 と 1 しか受け付けない**：0.5 を入れた NDU は NDT 出力は通るが、`S_ANALYSIS.exe` が LOG に `ｴﾗｰｺｰﾄﾞ＝ 825 【部材非線形性自動設定データ：適用データの抜出し量補正係数の値に誤りがあります】` を書いて止まる（5.2-L03、2026-10-27、WebRamen R6g で確かめた）。通し配筋の伸出し量を半分にする（ΔLy/2、設計計算例 RC ラーメン高架橋 III-9 ⑥）ような中間の値は表せない。JRSNAP 自身の要素分割は剛域に隣接する要素の端を 1 にする（操作説明書 2-36）。
- `JLoadInfo<n>=ケース, ,節点,増分,H,N,M,名前`：0 の成分は空白（1文字）で書く。値0の荷重の行を書くなら、少なくとも1つの成分に 0 を書く（WebPier は N＝0 と書いた。3つとも空白の行を JRSNAP がどう読むかは確かめていない）。
- 荷重の行が1つもない基本ケースは、解析はできるが荷重図（S_LoadPicture）でページが省かれ、次のページの題名がずれる（スキル `structural-jrsnap-figures`）。

## 荷重の組合せ（SNAPConb・ConbAlpf）（2026-10-22、owner が 5.2-L03 の画面で直して保存した橋脚の NDU 1件と、その NDT・状態の読取りで観測）

- `SNAPConbNum=<n>`・`ConbNum=<n>`：組合せの数（同じ値）。組合せごとに `SNAPConb<i>` と `ConbAlpf<i>` が1行ずつ。
- `SNAPConb<i>=ρm,αf,向き,0,係数×基本ケース数,空白で15欄まで,0,0`
  - 第1欄 ρm（材料修正係数、1 か 1.2）・第2欄 αf（基礎の支持力修正係数、1 か 2）。組合せごとに違ってよい。NDT では組合せごとに `DL    1.20`（ρm）・`DA                            2.0`（αf）の行になる。
  - 第3欄は載荷の向き：0＝正向、1＝逆向（JRSNAP の `G_intConbHoko`。読込み後の状態で確認）。NDT の名前の `_正向`／`_逆向` はこれで決まる。
  - 第4欄はこの1件では常に 0（応答変位法の接尾辞 `G_intConbOuto` の欄と推測しているが、未確認）。
  - 係数は基本ケースごとに 1（使う）か 0（使わない）。15欄に足りない分は空白（1文字）で、最後に `0,0`。
- `ConbAlpf<i>=係数×基本ケース数`：`SNAPConb<i>` の係数と同じ並び。
- `DataInfo` 第17・18欄も ρm・αf（組合せ1の値と同じに書かれていた）。NDT の ρm・αf は `SNAPConb` の組合せごとの値から出る。
- 例（基本ケース9、上り線＝ケース5・下り線＝ケース6、4つの (ρm, αf) × 正向・逆向）：`SNAPConb1=1,1,0,0,1,1,1,1,1,0,1,1,1, , , , , , ,0,0` … `SNAPConb5=1,1,1,0,1,1,1,1,0,1,1,1,1, , , , , , ,0,0`、`SNAPConb8=1.2,2,1,0,…`。5.2-L03 の読込み（スキル `structural-jrsnap-input` の open-save）は8組合せの ρm・αf・向き・係数をすべて書いたとおりに保持した。
- 画面で保存し直したこの NDU では、`FootInfo1` の末尾の2欄（回転ばねの最終勾配の比の逆数 20 と未設定値 `-3.402823E+38`）が消えて12欄になっていた（WebPier が書いたものは14欄。open-save の補助で保存し直したものは14欄のまま）。画面のどの操作で消えるか、解析に影響するかは確かめていない。

## 杭基礎の NDU（2026-10-25、JRSNAP 5.2-L03。5.3 体験版の JRSNAP_Input のソースと、見本 `Batch/tests/JRSNAP_Ver5.2-L03/01_サンプル(V53)：RC橋脚L：RC/` の NDU・NDT の読取り、WebPier が書いた NDU の本物の解析で確認）

- 見本は壁式橋脚が 8 本の場所打ち杭（φ1.0 m、L=19 m、3・2・3 本の列）の上にある骨組。杭は列ごとに 1 部材（`MemberOkuyuki`＝奥行き本数）、杭頭はフーチング底面の節点。
- **要素分割**（JRSNAP_Input の `mdlRenkei.cs`）：層の境界で切り、層の中を杭径 D ずつ切る。余りが 1.5D 以上なら D で切って残りを再び処理、D 超 1.5D 未満なら半分に、D 以下なら 1 要素。
- **要素ごと**（`JibanShogenInfo`）：Kh＝短期（非線形）の水平地盤反力係数、有効抵抗土圧は層内を要素長で線形補間して 0.1 に丸める。
- **節点ごと**（`SuppotInfo` の 10 値）：Kv・Rmt1（押し降伏）・Rmt3（引き降伏）・Kv2（第2勾配）・Rmt2（押し終局）・Rmt4（引き終局）・Kv2（第2勾配）・Kv3（引きの第1勾配）・Kv4（引きの第2勾配）・Kv4（引きの第2勾配）の順。値＝ばね区間内の要素の半分の長さ（⊿l）×層の値の和。区間は max(層の上端, 1/β) から、引き側は層の下端、押し側は min(層の下端, L−最小根入れ) まで。杭先端の節点は先端ばね・耐力を足す。丸めは Kv を 0.1（0.1 未満は 0.01）、Rmt は 0.01 に丸めてから 0.1。float32 ではなく正確な Decimal で再現でき、例外は同値（2086.25）の丸めだけ。
  - **杭先端の節点**（先端ばね・耐力を足した節点）も同じ 10 値の並び（2026-10-30、JRSNAP 5.2-L03 の本物の解析で確認、WebRamen R6）。例：`100895.3,1979.2,282.7,32829.3,4618.1,329.9,32829.3,28827.3,522.5,522.5`（Kv 100895.3・押し降伏 1979.2・引き降伏 282.7・第2勾配 32829.3・押し終局 4618.1・引き終局 329.9・第2勾配 32829.3・引きの第1勾配 28827.3・引きの第2勾配 522.5・522.5）。
  - **ばね区間の外の節点**（2026-10-30、JRSNAP_Input 5.2-L03 の連携を画面なしで動かして確認、スキル structural-jrsnap-input の soil-link の手順）：区間が要素の途中から始まり、その要素の上の節点が区間の外（区間の始まりより浅い）のとき、その節点はばねを持たず、上の節点の下半分のうち区間に入る長さも**要素の下の節点にまとめる**（例：押し側の区間が 7.233 m から、節点 7.000・8.000 m の要素で、7.233〜7.500 の 0.267 m 分を 8.000 m の節点に足し 1.267 m 分にする）。区間の中の節点は今までどおり上下の半要素。区間の終わり側も同じ扱いと見ているが、終わりが要素の途中で下の節点に半要素分がかかる例はまだ見ていない（推定）。
  - **押込み側が 0 の節点**（同じ確認と、5.3 の逆コンパイル `mdlRenkei.cs` の `GET_Dat_Kv`）：押込み側の Kv が 0 で引抜き側の Kv3 が正なら Kv を `0.01`、Kv2 が 0 で Kv4 が正なら Kv2 を `0.01` にする（第7欄の Kv2 も同じ）。制限値（Rmt）は 0 のまま。0 と書いた NDU も解析はできるが、入力データリストの印字は 0.001 になり、JRSNAP_Input が連携した NDU（0.01）と違う。WebRamen は 2026-10-30 からこの決まりで書く。

## DataInfo・ExOptLoad と NDT の対応、奥行き本数、基礎種別（5.2-L03 で確かめたこと、2026-10-27）

WebRamen の柱列骨組形式（R10b・R10e）で調べた。見分けやすい値（分割数 400、増分荷重の分割数 1234、第7欄 777、第8欄 888、`ExOptLoad` 第2欄 1.37）を書いた .ndu を、JRSNAPHeadless の `run --analyze false` で .ndt にし、操作説明書（5.2-L03、PDF 502〜505・606 頁の DA カードと LOAD カードの表）の欄の位置と照らした。[R]＝実アプリ、[M]＝操作説明書、[I]＝推定。

- `DataInfo` は DA カードの3行目（`       400     1.000   14 1234  200  777       888`）に出る：第3欄 分割数（1〜10 列）、第19欄 目標変位（11〜20 列）、第4欄 制御節点（21〜25 列）、第5欄 **増分荷重の分割数 MDV**（26〜30 列）、第6欄 限定増分荷重の最終ステップ **LiMiT 3**（31〜35 列）、第7欄 **M-θ（M-φ）諸元の固定ステップ数 LiMiT 4**（36〜40 列）、第9欄 LiMiT 5（41〜45 列。空欄なら空白）、第8欄 強制終了ステップ数（46〜50 列、LiMiT 6 と見られる）。[R][M]（第8欄＝LiMiT 6 は [I]）
- LiMiT 4・LiMiT 6 は「0」と空欄で処理が違う（0 は「ゼロステップ」で実施）。使わないときは空欄にする。[M]
- **`ExOptLoad` 第2欄は荷重の増減係数**：LOAD カードの **JALF**（21〜30 列）に出る（`LOAD               0      1.37`）。第1欄の LD（20 列）は正向 0・逆向 1（組合せの逆向の旗から出る）。[R][M]
- 奥行き本数は `MemberOkuyuki` と、その部材の要素の `NonLinInfo` 第8欄（ALF）の両方に書く。地盤ばね（.sdc の値は奥行き本数を考慮した値）には掛けない。`ElementInfo` 第1欄 0 は線形の要素で、第9〜11欄に A・I・E を書く。M-θ・M-φ を自動算定する要素の A・I は JRSNAP が断面から求める（R10b の調査、操作説明書と Batch の見本）。
- **`DataInfo` 第22欄（基礎種別 KT：0 杭基礎、1 直接基礎（一般）…）は解析の結果を変えない**：設計計算例 ＲＣラーメン高架橋の 0720（杭基礎、2 Case）を 0 と 1 で解析すると、.LOG・.EMG・.DB2・.ATR・.CSV・.OPT・.LP3 は同じバイト列で、.DB1 は 4801 バイト目（0 始まりで 4800）の1バイト（KT の値そのもの、0→1）だけが違った。ほかの結果ファイル（.KG*・.DSP・.FMT・.OUT・.PDN・.R10 など）は暗号化 zip で、毎回バイト列が変わるので比べられない。[R]

## 要素荷重 `MLoadInfo` の iT 4・iT 6 の向き（2026-10-28、JRSNAP 5.2-L03 の本物の解析で確認。WebRamen の柱列骨組の受入テスト）

- 書式：`MLoadInfo<n>=<ケース>,<要素（開始）>,<要素（終了）>,<増分指示>,<iT>,<AML1>,<AML2>,<WM1>,<WM2>,<WS1>,<WS2>,<説明>`。載る要素が1つなら要素（開始）は空白（`1, ,36,0,6,1.79, ,98, , , ,受け台`）。
- **iT 6（要素軸方向の集中荷重、kN）は i→j の向きが正**：AML1 は要素の i 端からの距離（m）。柱の要素を上の節点を i 端にして書くと、下向きの荷重が正の値。確かめ方：DB1 の step 0（CASE1 の死荷重だけ、`LoStepNo`＝0）で、荷重の入った要素の s·(Nj−Ni) − w·L が書いた P と 0.05 kN 以内で一致（s＝−1：軸力は圧縮が負）。説明書（表2-74〜76・付表2-78）は iT 4・7 だけ「i→j を正」と書き、iT 6・14 の向きは書いていない。iT 14（連続要素の軸方向の集中荷重、起点要素の i 端から）は未確認。
- iT 4（平行な等分布荷重、柱の自重）も i→j が正（上が i 端の柱で下向き＝正）。
- **M-θ の両端の短いばね要素（長さ 0.010 など）に iT 4 を範囲で掛けても、その要素の軸力の差 Nj−Ni は 0**（w·L の分が軸力に入らない）。剛な要素・弾性の要素では s·(Nj−Ni)＝w·L。部材の全長×w と、要素ごとの差の和は、ばね要素の分だけ合わない（例：w 83.8 kN/m・ばね 2 本で 1.676 kN）。
