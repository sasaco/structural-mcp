# JRSNAP の NDU の項目を読む・編集する

- 断面・材料・配筋のキーとフィールド：`references/section-fields.md`
- 直接基礎・支点・全体の設定、版の保存で足される項目、読込の制約、節点番号の順・破壊形態（`NonLinInfo`）・節点荷重（`JLoadInfo`）、荷重の組合せ（`SNAPConb` の ρm・αf・正向／逆向、`ConbAlpf`）、両端固定 M-θ 部材の Vmu・Vud のチェック（`DataInfo` の最後の欄）：`references/ndu-format.md`
- フィールドの意味は、特定のモデルで観測した対応を含む。各資料の「確認範囲」を見て、別の版・断面形状・案件へ無条件に当てはめない。
- 公式の説明：JRSNAP Ver5.2-L03 操作説明書（JRSNAP のインストールに付く PDF。T形断面 100頁、引張鉄筋段数 101頁・表2-33、DR の入力 103頁・図2-70、フランジ内軸方向鉄筋 105頁・図2-71・表2-36、主筋段数 90・530頁）。

## 編集前に確認すること

対象ファイル、入力キー、変更前後の値を利用者の最新の指示から特定する。ファイルごとに異なる指定を一括置換で混同しない。過去の事例の数値・件数は今回の既定値にしない。

`git status --short` と現在のファイルを確認する。既存の未コミット変更・ステージ済み変更を保持する。追加入力の訂正では、元の値が既に変更済みの場合があるため、現在の値から最新の指定へ更新する。

計算表などへ値を転記するときは、元 NDU のファイル名、断面番号、キーとフィールド番号、単位、転記先、換算方法を残す。梁高さ・材料強度のような転記値と、全幅・組数のような換算値を区別する。転記側でどちらの引張側の主筋を選ぶかなどの規則は案件の判断で、NDU の配筋を反転・変更する指示ではない。

## Shift-JIS を保持する編集

`.ndu` は Shift-JIS。表示の文字化けをファイル破損と取り違えず、読み取りには CP932 を明示する。PowerShell の既定エンコーディングで `Set-Content` / `Out-File` に書き戻さない。

ASCII のキーと数値だけを変更する場合は、`[IO.File]::ReadAllBytes()` で読み、バイト列へ限定置換する。確認済みの方法は、`[Text.Encoding]::GetEncoding(28591)`（Latin-1）で全バイトを可逆に文字へ対応付け、ASCII 部分を置換して同じ Encoding の `GetBytes()` で戻す方法。これはファイルの文字コード変更ではない。日本語の表示・編集にはこの中間文字列を使わない。

日本語を編集する場合は CP932 の例外フォールバックを用いて変換不能文字を検出する。対象外のバイトを保存前後で比較し、全体の再エンコードによる変化がないことを確認する。

行頭の完全なキー形式とカンマ区切りのフィールド位置を指定して置換する。ファイル全体への `16,250` のような無条件置換は避ける。元の改行、末尾改行、空白、行順、ヘッダーを保ち、変更不要の行を再構成しない。例（`SectFrangeJiku` の第2・第3フィールドだけを変える）：

```regex
(?m)^(SectFrangeJiku\d+-\d+=[^,\r\n]+,)16,250(?=,)
```

PowerShell/.NET で置換文字列を `'${1}13,300'` とすれば、第1フィールドまでを保持して径・間隔を変更できる。元の値がまだ存在する場合の例で、既に編集済みのファイルにそのまま適用しない。対象の件数は実ファイルで数える。キーの番号を振り直さない。

## 検証して保存する

1. 保存前のバイト列を保持し、実データから置換候補・件数を確認する。複数ファイルなら、全対象の変更案を先に検査する。
2. 変更した各行が指定キーに属し、指定フィールド以外が同一であることを確認する。対象外の行はバイト単位で一致させる。件数が想定と違えば、対象キーや現在値を調べてから進める。
3. 読み取り後にファイルが他の処理で変更されていないか再確認し、`[IO.File]::WriteAllBytes()` で保存する。保存後に再読込して予定したバイト列と一致することを確認する。
4. `git diff --check` と差分を確認する。対象外のファイルを含む一括作業では、対象外ファイルの SHA-256 が不変であることも確認する。ステージ済みの変更があるときは、作業ツリーの今回の差分と既存の差分を区別する。git の保存版が LF で作業ツリーが CRLF のときは、改行だけ正規化して保存版と比べる。

ファイル単位の変更件数と検証結果を報告する。文字列置換と差分検証は、JRSNAP による読込・解析の検証とは区別する。`.ndu` 編集だけでは `.ndt` や解析結果は更新されない。アプリで開いて保存する作業と解析実行はスキル `structural-jrsnap-input`。

## 見本を使った作成依頼で既存ファイルがある場合

まず既存内容を照合する。既に掲載入力が一致するなら、作成を装うための再書込みやヘッダー変更はしない。既存を採用したこと、変更件数0、読込検証の版と方式、未確認項目、再解析の有無を区別して報告する。PDF に根拠がない値（旧絶対パス、PDF に載らない剛域や安全係数など）は保持し、独自の値で埋め直さない。

- 案件の指定値・編集の記録（どのファイルのどの断面をいくつにしたか）・転記先の表：その案件の repo。
- WebPier が NDU を書く実装・決定・受入：WebPier の repo のスキル `webpier-jrsnap`。
- 資料には根拠と確認範囲を残す。利用者から教わったこと、ファイルで観測したこと、マニュアル等で検証したこと、未確認事項を区別する。個別案件の指定値・観測件数を一般仕様にしない。訂正は該当記述に反映し、矛盾する記述を増やさない。
